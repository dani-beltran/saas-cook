# Personal appearance and profile picture

## Scope and decisions

Extend Personal settings → Account identity with profile picture controls and an Appearance section. Only authenticated, verified, active human users with completed MFA may access their own settings. No organization membership, tenant policy, OpenFGA model change, service account, billing or general file capability is involved. This extends UI-01, identity and R-LIFECYCLE; it does not claim R-FILES or the Phase 6 account-deletion/restore journal.

Color mode is now an intentional personal exception to the prior developer-only theme design. Light, Dark and System persist in `identity.user.theme_mode`; NULL preserves the developer's configured fallback for existing/new users. Palette, typography, radius, shadows and density remain developer-owned. A monotonically increasing theme revision rejects stale changes. Identical saved modes are safe retries. Only mode and expected revision are accepted; no CSS or arbitrary configuration is accepted.

Both server document roots and viewport metadata share one request-cached authenticated snapshot. The HTML mode resolves before CSS paint without a local-storage bootstrap or hydration suppression. Anonymous/unavailable identity falls back to the product configuration. The client updates the document attribute and metadata immediately; native CSS color-scheme/light-dark continues to resolve System and follow OS changes, including portals/native controls. Client theme writes are serialized while the latest selection remains visible; failures reconcile authoritative state before rollback. Snapshots are bound to user/session; mutation headers assert the expected user but never authorize ownership. This closes a shared-browser cookie/account-switch race.

Browser memory caches refresh on focus, visibility, a 30-second visible-tab interval, and same-origin BroadcastChannel invalidation. Messages carry no trusted values. No persistent unscoped theme storage or preference cookie can override the database or another account. Late responses from another session are discarded, and concurrent avatar/theme responses merge only their own fields.

## Avatar storage and lifecycle

Use the existing identity `user.image` field as the sole display pointer. It contains only a server-generated relative `/api/auth/avatar?version=<uuid>` URL after upload. Better Auth's session endpoint returns this same field. Existing arbitrary image URLs remain untouched during migration but are never fetched by the UI. The identity route allowlist and disabled provider update-user endpoint prevent arbitrary image assignment. No object keys or target users are accepted as mutation fields.

A private `identity.user_avatar` row stores at most one 512 KiB normalized WebP per user, plus an opaque operation/version UUID. PostgreSQL is the durable avatar-specific store; the existing disposable PostgreSQL installation supports the real journeys. This consciously avoids introducing general S3/file APIs or an external-object saga for a tiny bounded personal asset. Tenant web/worker roles have no avatar-table access; only the existing restricted identity role can read/write it.

Upload accepts raw JPEG, PNG or WebP bodies, up to 5 MiB (labelled 5 MB in the UI). Streamed bytes are counted even without Content-Length; JSON requests are capped at 1 KiB. A 15-second body deadline, two concurrent decodes per process and a shared per-user 30/minute mutation limit bound work. Actual signatures, decoded format, maximum 8,192 pixels/side and 16 million pixels are checked. Sharp 0.35.4 rejects decoder warnings/malformed input, auto-orients, center-crops/resizes to at most 512×512, re-encodes WebP and drops EXIF/ICC/XMP metadata. Decoding has a five-second timeout. Originals are never written to disk or storage. The UI retains the existing image until the server commits.

Personal session lookups disable implicit provider renewal; the normal session endpoint retains its existing renewal workflow. After decoding, each operation takes the shared user lifecycle fence, revalidates the session/readiness, then locks the user row. Expected avatar version provides compare-and-swap; a UUID operation key permits replay of the current identical upload. Pointer, bytes and allowlisted audit action commit together, with a final database-clock session-expiry check. Replacement discards the previous bytes in the same transaction. Removal clears bytes and pointer atomically but keeps a small version tombstone, preventing a delayed initial upload from resurrecting a removed picture. No pending object exists to abandon. Physical space reclamation follows PostgreSQL autovacuum; backups follow deployment retention. Account row deletion cascades the avatar row; full self-service account deletion remains the existing Phase 6 boundary.

Delivery requires a current verified owner session and the exact current version, uses image/webp, nosniff, same-origin resource policy and private/no-store. Old versions, other users, missing/revoked sessions and bearer principals cannot retrieve it. Initials are consistent in Account/sidebar, with fallback for unavailable images. The normalizer's upstream contract is documented in [Sharp input safety](https://sharp.pixelplumbing.com/api-constructor/) and [output metadata behavior](https://sharp.pixelplumbing.com/api-output/).

## Deployment

Apply reviewed additive migration `0009_personal_settings` with the migration role before starting the new application. Existing rows receive NULL mode and revision zero; no image/history is rewritten, no backfill or authorization publication is required. Snapshots and journal are included. Use `bun install --frozen-lockfile` and rebuild the application image for the direct Sharp dependency and native binaries. Next explicitly externalizes Sharp; the web package also pins it so standalone tracing can resolve its platform binaries from the application root. This exact framework dependency is documented in Knip. The image gate loads the compiled identity/health route as well as exercising JPEG/PNG/WebP normalization.

There are no new credentials or environment variables. `IDENTITY_DATABASE_URL`, `AUTH_SECRET`, `APP_ORIGIN` and independent readiness retain their existing roles. Production PostgreSQL must be durable (the Compose databases are explicitly disposable test services), backed up, encrypted and monitored for storage/WAL/autovacuum. Budget at most 512 KiB of active avatar payload per account plus normal database overhead and backup retention. Keep these endpoints out of CDN/shared caches; allow cookie forwarding and the three mutation headers. Configure ingress body limits to permit 5 MiB raw image bodies and bound request time/concurrency; the application independently enforces its limits. Do not expose the identity database or avatar table publicly. General S3 configuration is not required for this feature.
