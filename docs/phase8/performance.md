# Customer image performance and Commercial contention

Run from the repository root with the pinned Bun/Node toolchain and Docker available. The full and smoke commands provision their own disposable services; they never reuse or reset development services:

```sh
bun install --frozen-lockfile
TEST_IMAGE=saas-cook:phase8-performance bun run image:build
TEST_IMAGE=saas-cook:phase8-performance bun run phase8:performance:smoke
TEST_IMAGE=saas-cook:phase8-performance bun run phase8:performance
```

The smoke has a 2-second warm-up and 30 measured seconds. Full acceptance requires a 60-second warm-up and at least 30 measured minutes. Both modes keep 100 tenants, 1,000 memberships, 100,000 Projects, 50 simultaneous clients (25 RPC and 25 REST), one tenant owning 50% of Projects and receiving approximately 80% of operations, and the Phase 3 60/20/10/10 read/update/create-delete/share-revoke mix. Runtime flags cannot lower the full workload. Smoke reports always set `acceptanceEligible: false`.

All customer operations cross TCP into the exact non-root customer image's Next HTTP routes. Setup seeds only disposable database records; signed Better Auth cookies must pass the actual image's identity adapter and an anonymous request must be rejected before load. No fixture identity routes or headers exist. Each client has its own update/share targets, preserving meaningful first-attempt availability without intentional version conflicts. Creates are immediately read; shares are confirmed through the recipient; revocations must immediately deny that recipient. A separate member sees exactly 1% of the initial hot-tenant candidates, including empty continuing pages. Every sparse row is checked against that explicit 500-Project allowlist; an unauthorized or duplicate row aborts the run without using the availability error budget. There are no automatic request retries, and warm-up failures also invalidate the run.

The Commercial-local preset enables platform and private S3 files and retains the finite local usage ledger/quota path. Stripe and external analytics are explicitly disabled for this local contention run. Every 120 seconds an authenticated hot-tenant owner uploads, verifies, dry-runs and submits a 20-row import, while a cold-tenant member submits an export over exactly 20 stable, authorized Projects. The real worker consumes both jobs. The export principal is intentionally bounded to the supported export size; an owner export of 50,000 Projects would violate the existing 1,000-row product limit. Export downloads are reauthorized and parsed to verify the exact permitted row set and field headers; missing, extra and duplicate rows fail. Jobs must complete, at least one must complete while the reference load is active, and all jobs must drain within 120 seconds after submission stops. The maximum 15 full-run imports stays within the existing 20-job tenant bound without deleting history or increasing limits.

Usage visibility samples the earliest outstanding successful create per tenant, identifies its immutable ledger sequence, and polls the real HTTP billing snapshot until its watermark includes that event. This measures create-submission-to-dashboard-data visibility conservatively, including request and poll latency. Pending samples cannot silently disappear. Provider billing throughput and rendered browser refresh are separate evidence.

Existing targets remain binding: p95 read <500 ms, write <800 ms, authorization fence wait <100 ms, source-commit/create-to-readable <2 seconds, at least 99.9% eligible first-attempt success, and usage visibility <60 seconds. Expected post-revocation denials are separate. The report records p95/p99/max, revocation-writer fence waits, observed request mix and hot share, cold-tenant progress, storage/WAL growth, service identities/limits, host hardware, and pool/time-out settings. Every tenant must make successful progress with no gap above 60 seconds, including the initial and final measurement boundaries. Hot traffic may deviate at most five percentage points and each mix category at most two points, allowing bounded random variation while rejecting the wrong workload.

The image is unchanged. A read-only, hash-recorded Node preload subscribes to the existing authorization diagnostics channel, attributes revocation request context and counts FGA request types/context sizes. It records only bounded numeric histograms and timestamps in disposable `/tmp` files; no identity, token, URL or request body is retained. The observer adds real measured overhead. No permission result, database query, transport result or timeout is changed. Fence p95/p99 distributions retain ceiling-millisecond bins and are explicitly labeled conservative upper bounds; maxima retain their raw measured value. To evaluate the unchanged strict p95 <100 ms fence budget without rounding ambiguity, the observer also retains constant-size counts of every valid measured raw duration strictly below 100 ms and at or above 100 ms. The verifier requires the fixed limit, safe integer counts, total/count agreement and consistency with the histogram's boundary bin. The gate passes only when the below-limit count reaches the nearest-rank p95 position; an exact 100 ms sample is not below budget. Missing or corrupt counters fail closed, with no fallback to a rounded percentile. Verified web/worker proof validity also feeds the mandatory authorization/observer gate independently of the latency result. This measurement correction changes no workload, application locking or budget. Earlier failed receipts remain failed: raw values in their `(99,100]` bin cannot be recovered or retrospectively accepted. Missing web telemetry, missing revocation waits, malformed observations, over-limit contextual tuples, persisted graph tuples or any tuple write fail the gate. Worker telemetry is retained separately so its contention is visible.

`performance-isolated.ts` is the required entry for every workload mode. It creates a fresh `phase8-perf-<random-id>` Compose project from `infra/phase8/compose.performance.yaml`: separate application/control PostgreSQL, OpenFGA, S3 and mail capture; dynamic ports bound only to `127.0.0.1`; and three project-owned local disk volumes. It refuses preexisting project containers, volumes or networks. Exact fixture ports are mapped into that project's Docker service DNS on both Linux and Docker Desktop; no shared network, host gateway or ambient S3 credentials are used. The underlying driver rejects missing wrapper configuration/IPC.

Before seeding, each data volume must use the ordinary local disk driver and show at least 8 GiB free. A bounded capacity probe every 30 seconds stops the workload if any filesystem has less than 1 GiB available or cannot be observed. The total sample budget is 15 seconds; teardown has a separate 45-second budget. These guards are not filesystem reservations or production capacity claims: host-wide free space can change between samples. Database storage is disk-backed, unlike the historical 1 GiB development tmpfs. The previous full attempt exhausted that shared tmpfs after roughly 26 minutes; that interrupted attempt remains failed and is not performance acceptance.

An `isolation-ready` event names only this attempt's containers and its immutable `artifacts/phase8/performance-environments/<id>/preflight.json`, which records the image/mount/resource/port/capacity provenance. After the driver cleans its own image, bucket and databases, it asks the wrapper to stop sampling and remove only its labeled resources and exact Compose project/volumes. The wrapper closes and flushes the retained workload log within five seconds before acknowledging cleanup; the log contains output received through environment finalization, while later receipt/warning output remains console-only. The driver awaits and hashes the preflight, final `cleanup.json` and finalized log before producing its performance receipt; cleanup or source mismatch invalidates the gate. Abnormal exits retain the workload log, failed wrapper receipt and best-effort teardown result. No shared service is stopped or reset. Before acceptance, reserve an otherwise idle host and record any intentional competing workload.

Each attempt keeps a uniquely named JSON report under ignored `artifacts/phase8/`, plus a convenience latest report. After isolated-resource cleanup it writes a P8-02 receipt with the report's SHA-256 digest, source commit/fingerprint, image identity and named gates. Full runs use `performance-full`; smoke uses `performance-smoke` and cannot satisfy the full gate. Full evidence requires a clean checkout. Failed cleanup invalidates the result. Failed gates and initialization errors must remain visible; a failed smoke is diagnostic evidence and does not permit lowering targets. Source changes or image commit/fingerprint mismatches require a rebuild. Acceptance belongs to the final integrated release candidate and the Phase 8 acceptance register, never to this harness's existence.

## Development verification

The required CI image job runs the explicitly scoped `phase8:performance:ci` correctness smoke after image acceptance and recovery. It uses the same isolated wrapper with `--ci-smoke`. The strict `performance-smoke` report and receipt remain failed when CRUD targets miss; the separate `performance-ci-correctness` receipt may pass only if read/write latency are the sole misses. Every other gate, including dependency health and isolated cleanup, still blocks. This CI contract was approved; it does not accept sustained performance. Ordinary `phase8:performance:smoke` remains strict. Manual CI dispatch with `phase8_full=true` runs the full workload instead and extends that job's budget to 90 minutes. A smoke receipt never satisfies the release's `performance-full` gate; the full run must use the final clean candidate and its exact image.

The first image smoke on 2026-10-22 exercised 3,953 reference operations with 100% first-attempt success. Sparse authorization, revocations, every tenant's progress, both worker jobs and usage visibility passed. The run failed the unchanged write target: p95 851.8 ms versus <800 ms (reads 424.3 ms, fence wait 75 ms, create-to-readable 781.1 ms, usage visibility 4.02 seconds). Other development checks were active on the same host; this is retained failed diagnostic evidence, not an accepted workload result or a reason to lower targets.

The raw report is `artifacts/phase8/performance-smoke-2026-10-22T17-39-49-696Z.json`, SHA-256 `d47bbb341ead72d5c7be9862326f1856fd6a604874e4c56b534ac1fe9462c9f2`. It predates P8-02 receipt integration and subsequent observer/cleanup/reporting changes. Twelve focused gate/observer/authorization assertion tests and strict TypeScript checks passed during implementation. Final-source image rebuilding and an isolated full run remain required.
