# Phase 8 — parallel PR delivery plan

Planning date: 2026-10-22. Status: planned; implementation and release acceptance pending. The [roadmap](../06-delivery-roadmap.md) remains the acceptance register. This plan implements the [Commercial release decision](../feature-briefs/commercial-template-release.md); PR IDs below are work identifiers, not opened GitHub PRs.

## Scope and ownership

Release the implemented Commercial template after accepted Phase 6/M2. Phase 7 and optional Backoffice release remain separate. Existing Backoffice code must continue to pass applicable regression checks; that does not accept its outstanding deployment, workload or release gates. A Commercial release with Backoffice disabled can finish while Backoffice feature development continues.

Assign one owner to each PR and one integration owner before implementation. The Phase 8 integration owner owns release scope, evidence applicability and shared CI/image changes; the Backoffice owner owns operator behavior and its separate acceptance. Assign a single migration/model integrator across both tracks. These are responsibilities, not assumptions about named staffing or a requirement to run agents.

Read the [architecture](../02-architecture-and-security.md), [data model](../03-data-model.md), [operations targets](../04-billing-usage-operations.md), [image contract](../07-ci-and-docker-image.md) and [verification rules](../development/verification.md) before changing their boundaries. Extend the existing harnesses rather than creating a competing migration, recovery or release authority.

## Execution waves

1. Merge P8-01. Resolve the upgrade-baseline policy early; identify actual release tags/fixtures rather than assuming a historical phase fixture is a supported product release. Agree image invocation, receipt fields and compatibility metadata with Backoffice.
2. Start P8-02, P8-06 and the test/fixture development for P8-03/04/05 in parallel. Backoffice BO-01/02 completion and BO-03–06 work can continue against existing domain contracts. P8-03/04/05 can develop against the current image while P8-02 lands; their final evidence uses its agreed interface.
3. Merge P8-02, then finish P8-03/04/05 independently as their prerequisites pass. Prepare P8-07 early, then run its final evaluations after relevant contracts and fixes stabilize. Extract shared remediations into prerequisite PRs reviewed by both owners.
4. Select the Commercial release candidate for P8-08 and run final evidence. Backoffice continues on its own branches; subsequent shared changes require an applicability review and affected reruns before inclusion in that candidate.

Critical path: P8-01 → image/evidence foundation → slowest of performance, recovery, compatibility and required remediations → applicable final evaluations/evidence → P8-08. Accessibility runs alongside this path but still blocks release if incomplete. The roadmap's 3–5 engineer-weeks remains provisional, not elapsed time or an estimate multiplied by PR count; re-estimate after P8-01 inventories gaps.

## Evidence and completion rules

- Store raw logs, reports and screenshots under ignored `artifacts/phase8/`; commit concise evidence indexes with immutable source/image identities, commands, environment/workload, results and limitations. Preserve failures and reruns.
- Maintain a coverage table in P8-01 linking every applicable roadmap gate to the owning PR and evidence. `R-AUTHZ-PERF` belongs to P8-03, expanded `R-RECOVERY` to P8-04, `R-IMAGE` to P8-02/05/08 and `R-SKILLS` to P8-07; ordinary Commercial security, lifecycle and domain requirements remain cumulative.
- Resolve upgrade support before P8-08. If no supported previous product release exists, record that finding and an explicitly reviewed initial-release support policy, with available predecessor-fixture coverage labeled accurately. Until resolved, upgrade acceptance remains open.
- Run existing source/type/unused-code, unit/integration, browser, Storybook, image and security checks appropriate to each change. Final release follows the full required CI and declared release matrix; new long-running harness commands must be implemented and documented before being cited as executed.
- New shared changes after evidence capture require source-delta review and affected reruns. A test-only change may justify retained behavior evidence; a changed workload, service, schema, dependency, runtime or image needs its relevant checks refreshed.
- This planning update records no passed Phase 8 checks and creates no release tag or GitHub PR.
