# ADR-0003: Independent recovery authority and security revalidation

Date: 2026-09-22. Status: design selected, infrastructure ownership/implementation/drill outstanding. Implements the design decision required by Phase 0; [operations §4.8](../04-billing-usage-operations.md#recovery-readiness-protocol) remains the canonical restore procedure.

## Failure domains and ownership

Choose a dedicated recovery AWS account in `eu-west-1`, independent of application staging/production accounts in `eu-central-1`. Its DynamoDB control table, retained S3 journal objects, signing/encryption keys, recovery identities and backup policy are managed by the **recovery/security custodian**, not the application host/deployment role. A second immutable journal copy in a separately administered archive account in `eu-north-1` protects acknowledged receipts against loss of the primary recovery region. No asynchronous replication success is inferred from a source write.

The application database, FGA database, host snapshots and their restore automation never include the authoritative recovery control plane. Separate schema/database names on the same application server are not sufficient independence. The application principal can submit allowed lifecycle intents and read scoped readiness; it cannot allocate epochs, reduce retention, delete journal records, issue revalidation approvals or reopen gates. Recovery operators authenticate through an independently managed identity provider/hardware credential and a separate administrative endpoint.

| Responsibility | Required owner role | Current assignment and readiness |
| --- | --- | --- |
| Recovery account/KMS/IAM/retention and independent backups | Recovery/security custodian, separate privileged credentials | Unassigned; organization must nominate a person/team before provisioning |
| Restore operation, data backups and deletion replay | Database/SRE operator | Unassigned; cannot approve its own independent authority evidence |
| Owner/identity proof and exceptional recovery approvals | Two authorized recovery reviewers | Unassigned; reviewers and evidence policy required before customer onboarding |
| Application deployment and host maintenance | Release/platform operator | Unassigned; no recovery-admin permission |
| Retention, recovery promises and provider cleanup policy | Product/data owner | Unassigned; business decision remains open |

These are concrete separation requirements, not claims that independent teams/accounts already exist. A small team may fill multiple ordinary roles, but recovery approval must retain an independent reviewer and separately controlled credentials. Shared organization-root compromise, malicious recovery custodians and simultaneous regional/account loss remain residual risks; retention locks do not prove immunity to every administrative action.

## Journal and completeness protocol

The independent service stores a versioned, minimal event: environment/installation ID, monotonically assigned sequence, request ID, subject type/opaque subject ID, lifecycle decision/effective date, retention scope, accepted ownership-resolution receipts, provider cleanup obligations, previous hash, payload hash and signer key ID. Store references/digests to sealed evidence; never put passwords, passkeys, magic-link secrets or unnecessary profile data into immutable records. Account subjects are global; organization subjects remain tenant scoped.

Proposed append protocol:

1. Application commits a frozen local intent; it cannot promise deletion scheduled or start purge yet. It submits the same request ID on retries.
2. The recovery service atomically inserts an immutable event and request-ID mapping and advances its sequencer using DynamoDB conditional transactions. The transaction checks the current installation/epoch and that append admission is open; closing the recovery barrier serializes against this same sequencer/control item. Duplicate ID with a different payload is rejected. Use a durable deduplication item rather than relying on the API's short idempotency-token window. DynamoDB transactions support conditional atomic updates, but their native request token lasts only ten minutes. [DynamoDB transaction semantics](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/transaction-apis.html).
3. Write that canonical signed event to unique versioned S3 keys in **both** independent journal stores. Apply the approved retention lock and verify exact versions/checksums. Existing content must match exactly on retry. A crash at any step leaves a repairable unacknowledged append; the service repairs gaps from its immutable event records. Never skip an allocated sequence or turn a missing event into an empty success.
4. Advance a contiguous durable watermark only after all preceding objects are verified in both stores. Persist a signed immutable checkpoint containing that watermark/hash in both stores, then return the receipt. Concurrent appends use conditional head updates; a recovered head never moves backwards. A DynamoDB head restored from backup is not sufficient completeness evidence: reconcile it with both immutable checkpoint chains before serving.
5. Application records the receipt and only then exposes scheduled status. Purge/completion, allowed organization cancellation, retention change and analytics suppression append further events; receipt retries do not undo accepted ownership transfers or duplicate provider effects.

S3 compliance-mode retention protects locked object versions, but Object Lock does not prevent newer versions or delete markers. Every journal reference includes version ID and digest; custodian policies restrict bypass/deletion and reads verify signatures/chains. [S3 retention semantics](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html). Choose the minimum independent journal retention as `maximum restorable backup age + maximum replay window + safety margin`; initial proposal is 35 + 30 + 7 = **72 days**, extended if any backup/hold lives longer. Approval of retention is a product/data-owner prerequisite, not a universal legal rule.

Completeness means every sequence through the signed durable watermark is present and verified, the latest authoritative head/checkpoint is known, and no accepted intent is stranded behind it. Listing a bucket, matching application row counts, or having a valid prefix of hashes cannot prove that the newest event is included. Before restoring service, reconcile pending appends and obtain a current checkpoint from the live authority. If the authority is lost/unverifiable, keep gates closed while custodians recover and attest a complete successor. No “initialize empty journal” fallback exists.

## Epoch and readiness barrier

An explicit fresh installation records a new environment/installation identity and empty-data attestation. Missing evidence means investigation/recovery, never automatic bootstrap. A recovery begins by closing readiness and revoking old process/provider credentials. The recovery authority allocates a fresh random epoch and monotonic counter; old epochs cannot issue current effects even if their application database is restored later.

Control state includes `{installationId, epoch, counter, state, journalWatermark, modelHash, approvedOrganizations, evidenceHash}`. `state` progresses closed → replaying → revalidating → rebuilding → verified → ready through conditional updates. Failures keep it closed. Only recovery services can approve transitions; the runtime reads the current epoch on protected operations and worker dispatch and fails closed when it cannot verify it. Cached readiness alone cannot authorize continued side effects after a gate closure. Before state changes or restoration, fence/drain old processes and revoke their credentials so an in-flight check cannot act across the transition.

During final replay, acquire a recovery-service barrier that **fences append admission and new sequence allocation/commit**, not only acknowledgements. The barrier transition and each append transaction serialize on the same control/sequencer item: a request is either committed before the barrier and included in the accepted tail, or refused/pending without a sequence or receipt. This closes the race in which an unacknowledged but already accepted event could otherwise fall beyond a captured watermark.

With append admission closed, record the last allocated sequence as the immutable barrier target. Drain/repair every already accepted append through that target, verify both journal copies and a signed contiguous checkpoint, and replay every event through it. Do not release readiness while an allocated event is unarchived, unverified or absent from the restored state. A timed-out caller does not remove an accepted event from this obligation. Receipt delivery for an accepted event may resume only after replay proves its lifecycle restrictions in the current epoch.

Conditional readiness release checks the same epoch, barrier token, sequencer target and durable watermark, plus graph manifests and revalidation evidence. Install the new runtime's gate before reopening append admission. Requests held outside the barrier remain pending with no receipt, no purge and no scheduled-success claim; a local freeze stays in place where it still exists. After release, accept a request only with the current epoch, freshly verified authorization/lifecycle state and a current-epoch local frozen intent. A pre-restore local intent/old worker cannot obtain a delayed receipt that bypasses the restored lifecycle state. Normal deletion commands again freeze before appending and acknowledge only after the independent receipt.

An interrupted barrier remains closed and requires reconciliation; lease expiry never automatically reopens append admission or readiness. Test append commit versus barrier acquisition, an already accepted but unarchived tail, delayed receipt delivery, and a pending request crossing epochs. This is a proposed concurrency/crash protocol, not executed recovery evidence. The canonical [recovery procedure](../04-billing-usage-operations.md#recovery-readiness-protocol) and [lifecycle lock order](../03-data-model.md#canonical-lifecycle-lock-order) continue to govern local freeze/re-admission.

## Identity and access revalidation

An application restore invalidates all saved sessions, API keys, support sessions, challenges, passwords/passkeys, MFA recovery material and linked-provider credentials. Rotate integration secrets before external effects. A restored credential, restored email address, or successful login with either proves nothing about current authorization.

Recover organizational authority using current, pre-enrolled evidence held outside the restored snapshot: an independently controlled enterprise directory for the scopes it owns, or recovery reviewers checking independently enrolled organization contacts and authority records. Email to an address found only in the snapshot is rejected. Directory authentication is insufficient to re-create application-specific roles/grants not owned by that directory.

Issue a scoped, short-lived recovery capability bound to the fresh epoch after verification. A verified owner reviews current members, teams, grants/parent relationships and tenant security policy through recovery services; a content hash binds the approval to the exact proposed configuration and source revisions. Changes invalidate that approval. Re-enroll credentials into the fresh epoch; re-admit members through normal seat admission; rebuild FGA only from approved relationships. Unknown organizations remain in owner recovery while verified organizations can reopen after deployment-wide replay succeeds. Security policy is not weakened to accelerate recovery.

For FGA-only restoration, use the less disruptive path only after independently attesting that the application store and security state are current/intact; bind that evidence to the new epoch and rebuild fresh graph namespaces. Uncertain recovery points use full revalidation. Accepted ownership transfer receipts do not automatically validate the successor: a deprovisioned/unverified successor keeps the organization gated.

## Feasibility, budgets and exit evidence

The original 15-minute data RPO is feasible only after selecting/measuring continuous database backup and restore services; journal acknowledgement targets **zero lost acknowledged lifecycle decisions** across the two chosen journal domains. Neither objective is measured by this ADR. A four-hour **full user-journey RTO is unbounded when required human owner verification is unavailable**. Do not promise it for all tenants. Keep four hours as the initial technical replay/rebuild objective for a rehearsed dataset and pre-enrolled, available recovery authorities; report human revalidation and blocked organizations separately while preserving end-to-end elapsed time.

Re-estimate Phase 6 with an additional provisional 2–4 engineer-weeks for the independent service, dual-store reconciliation and recovery approval UX/runbooks until a prototype proves otherwise. Product owners must either fund/operate pre-enrolled recovery authority and a measured response process, accept an explicitly conditional recovery objective, or revise the architecture. No restored-only access shortcut is permitted to satisfy an RTO.

The Phase 6 drill must exercise app/FGA mismatches, FGA-only proof, post-backup account/organization deletion/transfer, every post-backup credential and grant revocation class, interrupted dual-store append, missing checkpoint/gap, independent service outage, old projector completion, append allocation racing with barrier acquisition, accepted unarchived tail and delayed receipts across readiness/epoch release, owner unavailable, current directory evidence, seat reconciliation and provider/analytics cleanup. Record actual owners/accounts/keys, IAM-denial evidence, recoverability of the independent service, RPO, end-to-end RTO and per-organization resumed journeys. Design selection is complete here; those operational commitments and measured proofs remain open.
