# Independent deletion journal and recovery

The application protocol implements [operations §4.8](../04-billing-usage-operations.md#recovery-readiness-protocol). Hosting, backup scheduling, operator identity verification, physical process isolation, provider guarantees and recovery-time objectives belong to the deployment. A local database drill does not establish them.

## Independent store and command credentials

The control database must not be restored with the application/OpenFGA backup. Its sequence/hash journal head, append-only deletion entries, analytics subject/attempt registry, signed approval receipts, recovery checkpoints and security evidence must survive every restorable application backup plus the replay window. Replicate and retain this store independently; deletion of both history and its trusted head cannot be detected by a hash chain alone. Independent backup retention and monitoring must protect that trust anchor.

Provision the roles described in [module setup](platform-modules.md#runtime-and-upgrade). `bun run control:schema` uses only `CONTROL_ADMIN_DATABASE_URL` and is idempotent. Fresh bootstrap also initializes the control schema. The journal writer can execute bounded append/analytics registration functions but cannot update historical records, readiness or recovery approvals. Ordinary control access is read-only. The recovery application role has narrowly scoped functions and tenant tables, not DDL, owner or BYPASSRLS authority. Serve rejects migration/recovery/operator/admin credentials.

Packaged commands: `control-schema`, `recovery`, `recovery-fingerprint`, `analytics-report`, `flags-set`. Local aliases are `control:schema`, `recovery:run`, `recovery:fingerprint`, `analytics:report`, `flags:set`. The recovery command requires `RECOVERY_DATABASE_URL`, `CONTROL_ADMIN_DATABASE_URL`, `INSTALLATION_ID`, `OPENFGA_API_URL`, `AUTH_SECRET`, `RECOVERY_PUBLIC_KEY` and whichever configured storage/provider cleanup credentials the retained journal needs. Missing dependencies keep replay closed.

## Signed workflow

The independent approval issuer, outside the restored application, signs exact UTF-8 JSON bytes with Ed25519. The file envelope is `{payload, signature}`, both base64url. Claims use the exported `RecoveryApproval` type in `packages/authz/src/recovery.ts`: version 1, installationId, current epoch, unique nonce, operatorId, mfaAt, expiresAt, evidenceReference, source, action, mode, isolationEvidence, applicationHash and an optional enrollment. Approval validity and MFA freshness are at most five minutes. Do not keep the signing key in application configuration.

1. Independently verify the operator and isolate old application/worker processes and credentials. Sign action `begin`, mode `application`, current epoch, a SHA-256 application evidence hash and an independent isolation evidence reference. Run `bun run recovery:run --approval FILE`. The atomic control update closes readiness and returns the fresh epoch. Do this before restoring application data. No normal tenant work may resume during recovery.
2. Restore only the application database (and separately FGA if required). Sign `replay` for the fresh epoch. The command drains the global application fence, invalidates all restored credentials/challenges/sessions, clears grants/team links/API keys/integration secrets, cancels restored work and releases restored seat occupancy through shared transitions. All surviving organizations require owner recovery.
3. Replay the complete verified deletion chain under the independent journal barrier. Completed deletions are re-purged, including provider copies and post-backup analytics subjects. Accepted ownership-transfer resolutions remain independent evidence; they do not automatically authorize a successor. Provider-pending cleanup stops replay and keeps serving closed. Retry with a fresh valid approval in the same epoch; idempotent checkpoints survive interruption.
4. A fresh FGA store/model is published and the source/compiler binding is verified. For each identity to restore, independently verify its **current** identity/email and applicable policy, sign `enroll` with `{userId, verifiedEmail}` and source `independent-identity` or `current-directory`. Restored credentials and the old email alone are insufficient. Deleted identities cannot enroll. Enrollment creates no restored password/passkey/session or membership grant.
5. Sign `release`. Release re-verifies the application/model and requires the exact latest journal sequence/hash. Any new acknowledged deletion requires another replay first. Unverified users remain frozen and organizations remain in owner recovery even after the global gate opens.
6. Use the existing independently signed `owner:recover` procedure to establish current organizational authority. Verified owners explicitly re-admit members via normal seat admission and recreate current team/resource grants. New credentials must be enrolled in the new epoch. No restored membership, grant or old key is implicitly trusted.

Every action retains independent evidence, nonce, epoch and outcome. Forged/expired approvals, wrong epochs, missing/truncated journal history, model failure and interrupted cleanup fail closed. Reusing a nonce with different bytes fails. Already completed valid command receipts are idempotent.

For **FGA-only** loss, an independent system must prove that the application store is current and intact. `recovery:fingerprint` hashes current security, credentials, grants, policy/settings and integration state; obtain an independent signed `independent-system-attestation` with that exact hash and mode `fga-only`. The hash is checked again under the exclusive reset fence. Only this path preserves verified current credentials/access while rebinding to the new epoch. An uncertain application recovery point must use `application` mode.

The current domain is Organization → Project; Workspace inheritance was retired in the predecessor. Recovery invalidates direct and team grants rather than inventing a legacy parent hierarchy. Tests retain a real `pg_dump` before later grant/key/passkey/membership revocation, accepted ownership transfer and account/org deletion, then restore with `pg_restore` and prove old authority remains denied. Broader infrastructure fault budgets and live-provider evidence are recorded separately in [acceptance](acceptance.md).
