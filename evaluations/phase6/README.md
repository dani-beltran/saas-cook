# Phase 6 Commercial skill behavior evaluation

This explicit five-task evaluation extends the Commercial requirements in skills §5.8.
It does not relabel historical Phase 4/5 candidates, deterministic boundary checks,
protocol fixtures, or ingestion acknowledgements as new live-agent/provider evidence.
The two authors independently add an application workflow over the actual modules;
the controller imports each candidate's implementation and executes real restricted-role
PostgreSQL/OpenFGA/S3 behavior. No candidate change is promoted to the template.

The public briefs declare data-job creation, discovery/activity, account-departure
preparation, authoritative analytics settings, and diagnosis of five unsafe seeds.
The hidden assertions exercise the added workflow on real services; complete protected
application suites additionally cover immutable finalization, mapped imports/exports,
provider-pending cleanup, independent journals, late ingestion and recovery. The expanded
recovery controls include a full pg_dump/pg_restore with team/membership/credential
revocation after backup, and a delayed real FGA allow after independent epoch rotation.
Local provider fixtures remain distinct from actual live-provider release evidence.

Prepare before author dispatch:

```sh
node evaluations/phase6/prepare.mjs artifacts/phase6-acceptance/evaluation/release-new
```

The output records exact source/skill/reference hashes, template commit, two independent
candidate copies, customization, public briefs, unsafe review seed and evaluator controls.
Only the original Phase 4 report-parser helper is included as a dependency of protected
application runner tests; current evaluator assertions remain outside candidate edits.
All original application source, tests, migrations and configuration stay hash-protected.
Candidate-only source changes must be additive, and every actual author prompt/tool/reply
is retained as original Codex JSONL with exposed session/model/configuration metadata.
Never fabricate a transcript or infer an unexposed reasoning setting.

Run the initial author prompt in each candidate independently. Preserve the planned partial
stop with `capture.mjs`, seed the existing localized code customization with
`seed-customization.mjs`, then install each candidate with the frozen lockfile, and create a
retained real Project/migration checkpoint before the explicit same-session resume.
`observe-seeds.ts` runs five protective assertions against the unsafe fixture and records
their observed failures for author diagnosis. The authors may read observations, not hidden
assertion source. Author sandbox/network limitations and failed dispatches remain evidence.
The controller runs services with disposable synthetic configuration only.

After authors finish all tasks, verify the retained checkpoint, capture final source,
repeat the satisfied request, and require byte-identical source after that repeat. Then:

```sh
node evaluations/phase6/run-checks.mjs RELEASE_ROOT 1
node evaluations/phase6/run-checks.mjs RELEASE_ROOT 2

# Optional evaluator-owned gate serializes full integration against root mail consumers.
node evaluations/phase6/run-checks.mjs RELEASE_ROOT 1 RELEASE_ROOT/root-mail-ready
```

The controller verifies protected/control hashes before and after execution, retains every
attempt in a unique directory, requires the added workflow and expanded recovery cases,
then runs source/type/Knip/unit/full-integration/production-build checks. Fresh structured
reports must contain every original test file and no failing, skipped or todo cases.
Source must remain stable throughout checking. The supplementary `verify-regressions.mjs`
requires the frozen multiset of all original case identities, including duplicate titles,
and validates fresh candidate JSON reports against it. Its census comes from independent
root JUnit reports only after every original test source hash matches the pre-author
baseline; candidate reports never supply the expectations. `audit-transcripts.mjs` verifies
distinct sessions, same-session turns and actual successful candidate-local skill reads.
`finalize.mjs` requires these supplements, exact custom code preservation, successful
repair/repeat transcripts and post-repeat data/cleanup receipts. Preserve failed setup or
author attempts; a repair never erases its predecessor. Final acceptance additionally requires both actual
author transcripts, planned stop/resume, retained data/migration/customization evidence and
source-identical completed-request repeats. A controller exit alone proves none of those.

The optional generated `apps/web/next-env.d.ts` may be absent after a successful cached
build; it is excluded from source protection. `repair-reporter.mjs` handles only the exact
recorded reporter failure after all seven commands passed. It retains the original failed
result, revalidates protected/control/controller/source hashes, raw reports and command-log
digests, and creates a separate derived result reusing the same successful commands. It
does not convert application failures or skipped cases into success. The frozen executed
controller and all earlier attempts remain unchanged. See the
[execution record](../../docs/phase6/evaluation.md) for the release-1 result and repairs.

The host sandbox restricts edits to candidates. Read isolation additionally relies on
instructions, external controls, hash checks and transcript review; directory separation
is not an OS boundary against an unrestricted reader. No production/provider credentials
are supplied to the authors. A passing evaluation is bounded evidence for its five tasks
and recorded agent configuration, not universal skill reliability or live-provider erasure.
